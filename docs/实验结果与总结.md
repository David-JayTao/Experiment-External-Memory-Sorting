# 实验结果与总结

## 1. 实际完成范围

Week 3：二进制 Header + Directory + Data、固定容量目录、多个不等长段、创建/扫描/追加/查找、流式输出及输入输出缓冲。

Week 4：真正按 M 分块生成初始段、普通二叉归并计划、后序递归执行、两输入一输出缓冲的二路外排序。

Week 5：内部保存败者的 LoserTree、固定 M 个有效候选上限的置换选择、冻结/解冻、两个输入及两个输出块、三个实际工作线程、阶段 join、哈夫曼最优二路归并树。

Week 6–7：2k 共享输入块、每路队列、统一空闲池、末关键字最小预取、块跨路重用、败者树 K 路选择、双输出块、三线程阶段同步以及多轮主控。

Week 8：220 次端到端精确检查、机制与错误输入检查、实测 CSV、教学讲义、48 题验收问答。没有实现任务范围外的矩阵乘法、快排外排序、GUI、数据库或复杂线程池。

最终 CTest 结果：**Release 6/6 通过，ASan+UBSan 6/6 通过，TSan 6/6 通过**。

| 配置 | 核心 correctness 用时 | CTest 总用时 | 结果 |
|---|---:|---:|---|

CTest 六项分别为：`correctness`、`cli_help`、`reject_zero_block`、`reject_negative_memory`、`reject_bad_k`、`reject_missing_value`。四项拒绝测试预期程序返回非零，CTest 使用 WILL_FAIL 表示预期失败。

correctness 中的端到端检查数是：

- 14 组基本样本 × 5 配置 = 70：Project 1、Project 2、Project 3 的 k=2/3/4。
- M=1/3/8 × B=1/5/17 × 3 个 Project = 27。
- 40 个固定种子的小规模样本 × 3 个 Project = 120，包含非2次幂候选数量和 k=2–7。
- 50003 个整数 × 3 个 Project = 3。
- 合计 **220 次**。12 行 benchmark 还有独立的精确验证，不包含在这个220中。

基本样本涵盖空输入、单值、逆序、重复和负数、INT32_MIN/INT32_MAX，以及17/257/4099长度的随机、升序、逆序输入。所有端到端检查均检查数量、有序性、与 std::sort 逐项一致，并扫描全部中间归并段验证有序。

## 4. 指标口径

- N 是原始整数个数。M 是内排/候选数量，B 是每块整数数，不是字节数。
- runs 是初始段数。merges 是实际执行的归并组数。
- rounds 只对 Project 3 的多轮分组主控计数；Project 1/2 为0，使用 merges 描述它们的归并工作。
- reads/writes 统计成功的非空数据块 read/write 调用。头部/目录初始化、更新、演示读取和最终验证不计入。
- 这不是硬盘物理 I/O 计数。标准库缓冲和操作系统缓存都会影响实际磁盘访问。
- stages 是置换选择与 K 路阶段同步总次数，包括流水线排空；不是归并轮数。
- ms 是 `steady_clock` 测得的 sortFile 时间，包括输出文件创建、元数据写入、算法、线程创建和刷新；不包括输入生成、std::sort 参考及结果检查。
- 性能数据关闭 trace。开 trace 会把打印时间算进 sortFile，不能和此表直接比较。

### 5.1 段数与归并代价

N=50003 时，置换选择把初始段从196减到99，符合随机输入可能产生更长段的目的。升序输入可能形成一个很长的段；逆序输入通常无法延长到超过候选容量。不能将“平均约2M”当作每种输入的保证。

同样99个初始段，Project 2 二路归并98次；Project 3 四路分组得到 `99→25→7→2→1`，归并组数为 `25+6+2+1=34`，总4轮。第二轮的最后单段直接带过，因此不必每组都做数据复制。

15个数的手算实例还直接验证了最优二路计划：置换段长7、7、1，普通代价29，最优代价23。代价模型与最优树测试相互独立核对。

### 5.2 I/O 与耗时为何方向不同

N=50003 时，Project 1 的数据读写调用合计13964次；Project 2为12258次；Project 3为7970次，后者约少42.9%。但对应耗时约21.4、93.0、379.4毫秒，当前环境中并行版本更慢。

这是测得的结果。B=64意味着每块只有256字节；每个阶段新建并 join 三个线程，Project 3共有3948个阶段。数据仍可被系统缓存，小块文件 I/O 本身很快，线程管理和阶段调度开销明显。没有实现线程池是遵守课程“简单分阶段线程”的选择；不能为让表格更好看而忽略这一成本。

此外，三个模式没有严格控制相同的总内存字节预算：M一致，但K路拥有更多输入缓冲；元数据与树结构也不同。本表用于验证机制和观察趋势，不用于宣称某一种方法在所有硬件、规模上更优。

### 5.3 为什么块写不一定等于块读

置换选择一个输出内存块可能含不同段号，writeGeneratedBlock 会按段号分开写；K路可能在补齐某路头值时结束阶段并写出部分块。所以计数是实际调用次数，不是简单的 N/B 理论估计。所有不足一块的数据仍被写出并经过精确检查。

## 6. 开发中实际出现的问题与处理

1. PowerShell 默认读取中文文件时出现乱码。显式 UTF-8 后重新阅读任务书和讲稿，源码及文档也统一使用UTF-8。
2. Windows 默认环境没有可直接调用的 C++ 编译器，但 WSL 已有 GCC。最终使用 WSL 编译，CMake 下载到本地工具目录，不需要修改系统级工具配置。
3. 最初将大量小块测试数据放在 Windows 挂载目录，Project 1阶段测试用时约97.7秒。改用WSL原生目录后，同类运行明显加快。因此正式实验明确使用Linux用户目录，未把两种文件系统结果混在表中。
4. 本机WSL空闲退出后会重新启动，`/tmp` 构建目录随之消失。最终构建改到 `$HOME/.cache/ems-build-20261109`，避免临时目录生命周期影响复现。
5. 一次正在构建时接入下一阶段源文件，旧CMake源列表与更新中的引用短暂不同步，出现未链接 replacementSelection。随后按完整源列表重新配置并构建，通过阶段测试。最终检查期间不再边编译边修改源文件。
6. 代码审查补充了线程创建失败时先 join 已启动线程的收尾，避免仍 joinable 的 thread 析构导致 terminate。该处理经最终编译和正常运行验证；没有故意制造操作系统线程耗尽来声称覆盖这个异常路径。

以上只记录实际观察到的问题和审查改动，不虚构死锁、数据丢失或性能优化过程。

## 7. 简化假设与局限

- 归并文件保存全部历史段，不回收中间数据区；磁盘占用随归并计划累计增长。
- 排序数据受工作区限制，但目录、初始段下标列表和计划节点仍占O(R)内存。项目不是恒定总内存元数据系统。
- M是候选/内排容量，另外还有B大小缓冲、补齐败者叶、输出段号标签。固定 M 不等于进程总内存严格固定为4M字节。
- 文件格式直接保存固定结构，面向同字节序、同布局平台；没有跨架构序列化、压缩、校验和或掉电事务。
- 目录满、读取越界、常见文件错误会报错；不实现针对任意恶意文件的完整安全解析器。
- 输入输出必须是两个独立文件，路径别名/链接不能指向同一个文件。程序不提供通用文件身份解析。
- K路在缺少未完成路的头值时同步等待，保护顺序正确性；没有声称达到课件理想模型中的所有性能界。
- 测试在小规模至50003个整数上运行，足以跨越工作内存并触发多轮，但不等同于TB级磁盘压力测试。
- 同一工作目录中的固定测试文件名不适合多个程序并发运行；需要不同目录隔离。
- 已补充原生 MSVC 实测；MinGW、真实掉电、磁盘满、跨字节序及线程资源耗尽仍未测试。

课程要求范围内的核心算法和文档均已实现并通过上述检查；这些限制作为实现边界公开记录。
